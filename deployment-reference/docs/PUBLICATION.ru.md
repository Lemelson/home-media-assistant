## Предмет публикации

Проект показывает, как связать собственный Telegram-бот, локальный агент, Transmission и необязательный медиаплеер. Он распространяет исходники, искусственные тестовые примеры, пустые шаблоны и инструкции. Читатель устанавливает сторонние приложения отдельно и использует свои аккаунты. Публикация исходников не предоставляет доступ к какой-либо действующей установке.

Описание BitTorrent остаётся прямым: это функция передачи данных, в том числе отдачи другим участникам. Переименование функции в «облако», скрытие слова «торрент» или фраза «только для обучения» не создают разрешения на контент. В документации нет обещания доступа к любому фильму, освобождения от ответственности или анонимности.

## Решение по каждому материалу

| Материал | Условие включения |
|---|---|
| Собственный код и текст | Есть права на распространение; сохранены применимые уведомления |
| Заимствованный код | Установлены источник и лицензия, выполнены её условия; иначе не включать |
| Пустой конфиг | Только условные значения, без работающих ключей, аккаунтов и инфраструктурных идентификаторов |
| Пример диалога | Создан заново на искусственных данных; не скриншот личного чата |
| Лог или ошибка | Минимальный обезличенный фрагмент после ручной проверки |
| Чужой постер, логотип, шрифт | Не включать без подходящих прав и выполнения условий атрибуции |
| Фильм, аудио, torrent, magnet-каталог | Не нужны для публикации проекта; не включать |
| База, backup, cookies, SSH-ключ, конфиг сервера | Не включать |

Открытая ссылка не означает свободную лицензию. API-ключ разрешает доступ в пределах условий API, а не любое дальнейшее распространение результата. Даже собственная запись может содержать чужую музыку, людей или материалы с отдельными правами. Проверка прав нужна для конкретного объекта и способа использования.

Copyright Office США указывает, что получение и распространение охраняемых произведений без разрешения может нарушать исключительные права. Исключения, включая fair use, зависят от обстоятельств; надпись «личное использование» не является универсальным разрешением. [Официальный FAQ](https://www.copyright.gov/help/faq/faq-fairuse.html).

В ЕС решение ACI Adam требует учитывать правомерность источника при частном копировании. Это не единое разрешение на P2P-раздачу и не правило для всех стран Европы. Вопросы публичного распространения, персональных данных и предоставления сервиса требуют отдельной оценки. [Решение Суда ЕС](https://eur-lex.europa.eu/legal-content/EN/SUM/?uri=CELEX%3A62012CJ0435).

Наличие GitHub-репозитория, MIT или процедуры ответа на обращения не гарантирует защиту от требований. GitHub рассматривает обращения по своей [DMCA-процедуре](https://docs.github.com/en/site-policy/content-removal-policies/dmca-takedown-policy). Не выдавайте этот проект за юридически сертифицированный сервис. Для оценки конкретных действий и стран нужен профильный юрист. Дополнительные источники, включая российские нормы, приведены в [правовых заметках](../../docs/ru/LEGAL.md).

## Персональные данные и публичная поддержка

Telegram ID, история запросов, имена файлов, IP, сведения об устройстве и данные аккаунтов могут раскрывать информацию о людях. Включённые провайдеры получают соответствующие запросы; бот не превращает их в анонимные. Не обещайте пользователям полную конфиденциальность без анализа фактических потоков данных.

Исключение GDPR для некоторых исключительно личных/семейных действий нельзя автоматически переносить на публичный сервис. При его применимости оцениваются правовое основание, информация пользователю, сроки хранения, безопасность, обработчики и международные передачи. Даже если репозиторий не собирает данные установок централизованно, оператор собственной установки должен оценивать свои действия. [GDPR, статьи 2, 5, 6, 13 и глава V](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng).

В публичных issue просите искусственное воспроизведение. Не просите «пришлите всю базу/конфиг». Если нужен закрытый канал, договоритесь о нём до передачи сведений; сам приватный канал не делает сбор лишних данных необходимым.

## Проверка перед публикацией изменений

1. Соберите отдельную публичную копию из выбранных файлов; не архивируйте рабочий сервер целиком.
2. Проверьте diff, новые файлы, названия каталогов, сообщения коммитов, подпись автора, историю отправляемой ветки и архивы релиза.
3. Удалите секреты, реальные адреса/ID, личные пути, базы, логи и медиаматериалы. Используйте искусственные примеры вместо редактирования личного скриншота.
4. Проверьте происхождение каждого нового стороннего материала, лицензию и обязательные уведомления.
5. Из корня публичной копии выполните `python3 scripts/check_public_tree.py --history` после локального коммита. Установленная приватная защита публикации дополнительно проверяет назначение и отправляемую историю. Отсутствие срабатываний — ограниченное свидетельство, не абсолютная гарантия.
6. После push сверьте commit, состав опубликованных файлов и CI. Отдельно проверьте приложенные к релизу архивы: чистая ветка не доказывает чистоту старого ZIP.

В этом репозитории намеренно виден владелец GitHub: публичность под собственным аккаунтом не означает анонимную публикацию. Обезличивание касается частной инфраструктуры и данных, а не сокрытия происхождения репозитория. GitHub и внешние читатели могут сохранять копии. При утечке ключа отзовите его, затем очистите материалы и при необходимости обратитесь в поддержку платформы; переписывание истории само по себе не стирает все копии.
